# Step P2-4: faster look slicing in the phase 2 engine

Date 2026-11-04. Repo `~/research/evolveTrial-perf`, branch `perf/engine-cpp`, base HEAD 3bb0694. Not committed. Build
installed only into `dev/perf/lib/dev_p2_inc` (log `build_dev_p2_inc.log`); `dev_p2` was not touched (a gate runs
from it). Only the phase 2 engine changed; `src/simulate_chunk.cpp` and `src/r_semantics.h` (phase 1) have no diff.

Result: on every G3 design the chunk results, the `run_scenarios` tables and the `.Random.seed` left behind are
`identical()` to the 3bb0694 engine (`dev_p2`), so the G5 run on 3bb0694 covers this build. R23 is 1.40x faster at one
worker on a lightly loaded machine (1.59x under load 14), R01 about 1.02x.

## 1. Design

The P2-2 profile put 75.5% of R23 time in `slice_arm`, mostly at interim looks whose vs-reference gates then fail
(330k slices for 80k posterior evaluations). Two changes, both exact by construction rather than within tolerance.

1. **A cheaper slicer with the same outputs.** `slice_arm` is now three stages.
   - `slice_counts`: one pass over the registry giving the observed patients, status, events by interval (the same R
     `findInterval2` call as before), `n_pat`, `status_sum`, `events_total`. No allocation after warm-up.
   - `slice_pt`: person time by interval in one pass over the observed patients with K long-double accumulators. Each
     interval receives the same contributions, in the same patient-index order and the same precision, as the
     reference's one-interval-at-a-time `sum_ld`, so each `pt[k]` is the same double (`finish_ld` repeats `sum_ld`'s
     overflow and `-0` steps). The interval loop stops at the first interval with `obs <= cut[k]` only when the
     cutpoints are non-decreasing (checked per call); otherwise every interval is tested as in the reference. The
     reference's per-interval `contrib` vector and K scans are gone.
   - `slice_median`: `median_r` by `std::nth_element` into a reused buffer instead of a copy and a full sort. The
     selected order statistics are the same values, and the even case uses the same `mean_ld`, so the median is the
     same double. Any NaN still gives `NA_REAL`.
   `slice_arm` runs the three stages and is used everywhere it was used before (HC looks, finals, replay path).
2. **Lazy gate at vs-reference interim looks.** `interim_vsref` computes the counts stage for both arms, checks the
   two event-count comparisons, then the medians and the two median comparisons, then person time and the full
   `gates_pass_vsref`. The gate is a conjunction of comparisons on these quantities, so the decision is unchanged, and
   the slices are not read again after a failed gate (the finals re-slice).
3. **Final vs-reference analysis** reads the reference arm's events from `w.sl_ref` instead of slicing that arm a second
   time at the same time with the same cutpoints.

Not done: incremental bookkeeping across looks (carrying per-patient state from one look to the next). After items 1
and 2 the slicing share left is small, and carrying long-double sums across looks while keeping patient-index order
would add risk for little gain.

The 3bb0694 slicer is kept verbatim as `slice_arm_ref` (not called by the engine) behind the test hook
`.exact_slice_compare(enroll, te, rc, cal, max_fu, cut, K)`, which slices one registry with both and returns both
(the new slicer is run twice into the same `Slice`, first at another time, so stale buffers would show).

## 3. Identity

- **Slicer test** (`.exact_slice_compare`): 3,000 random cases, n from 0 to 300, K 1 to 8, finite and infinite
  follow-up caps, censoring off and on, tied event times, events exactly at a cutpoint, looks before first enrollment
  and at an enrollment time, NaN times (NA median path), base, rebalanced-like, repeated and unsorted cutpoints. All
  3,000 `identical()` over `n_pat`, `status_sum`, `events`, `pt`, `events_total`, `pt_total`, `median_fu`, `obs`, `st`.
- **All 10 acceptance designs, R = 2,000** (`p2_4_identity.R` on `dev_p2` and on `dev_p2_inc`, then `p2_4_compare.R`):
  per scenario the raw per-trial result of `.simulate_chunk_exact(1:2000, cfg, c(seed, scenario))`, plus
  `run_scenarios` at one worker with the capture's seed (900001, or 910001 for R04 and R26). **20 of 20 chunks, 10 of 10
  tables and 10 of 10 `.Random.seed` identical. 0 trials differ.** The relative 1e-12 allowance was not needed.
- **G3** (`g3_check.R dev/perf/lib/dev_p2_inc 2000`): **100 runs, 10 designs, 0 failed, PASS** (log
  `p2_4_g3_check.log`, rows `p2_4_g3_results.csv`; the script's fixed output `g3_results.csv` was moved aside and the
  committed P2-2 file restored with `git checkout`).
- **Package tests** (`dev/perf/harness/run_pkg_tests.R dev/perf/lib/dev_p2_inc`): **833 passed, 0 failed, 33 skipped,
  0 errors, 0 warnings** (831 before plus the 2 new expectations). This includes the replay test, so the replay
  instantiation with the new slicer still reproduces the phase 1 engine exactly on R01 and R23.

## 5. Mismatches with the plan or the brief

1. **Plan wording "incremental bookkeeping".** The change is a faster exact re-slicer plus a lazy gate, not state
   carried across looks (Section 1). The plan's constraint (identical counts, doubles within 1e-12, checked by a test
   that runs both) is met in the stronger form (bitwise identical).
2. **Core limit.** `g3_check.R` runs 4, 16 and 19 workers by design and has no worker argument. It was run as written at
   `nice 15` (about a minute of wall time); load rose from 10.9 to 13.5 during it. All other runs used one core (the
   package tests briefly use a few, also niced; and the two identity runs ran in parallel, two cores).
3. **`dev_p2` build time.** `dev_p2`'s DESCRIPTION shows it was built 2026-11-04 05:54 UTC, minutes before this step
   started. I took it as the 3bb0694 build named in the brief and did not rebuild it; the identity comparison is against
   that library.
4. **Phase 1 layer 1** (`dev/perf/harness/run_layer1.R`) was not rerun, since no phase 1 source changed (no diff in
   `src/simulate_chunk.cpp` or `src/r_semantics.h`).
5. **Unreachable stop.** The reference's "NA event time" stop cannot be reached (an event needs a non-NaN time, which
   makes `obs` non-NaN), so the test covers NaN times through the NA-median path instead; the new slicer keeps the stop.
