# Phase 3 plan: the exact engine for every configuration

Date 2026-11-04. PI ask: users get the fastest possible version whatever they call. Inputs:
`2026-11-04-phase3-coverage-inventory.md` (32 predicate items, Section 4 order, Section 7 merge hazard),
`2026-11-04-hybrid-seamless-speedup-note.md`, `2026-11-04-phase2-readout.md`. PI said go on 2026-11-04 to the
route "merge main, one general C++ trial loop with exact posteriors, then hybrid/seamless and binary, then V2".

## 1. Rules that hold for every step

1. A configuration the fast engines do not cover falls back to the R body. Users are never worse off mid-phase.
2. The supported-set predicate admits a frame only after both engines implement it. Admission without a port is the
   one silent-failure mode, so every predicate change lands in the same commit as its port and its tests.
3. Each step ships when it passes four gates:
   - **B (bit-identical).** The phase 1 C++ loop gives `identical()` output and `.Random.seed` to the R body on new
     acceptance frames that exercise the step's branches. Report chunk counts.
   - **S (statistical).** The exact engine against fresh R-body runs at fresh seeds, two one-sided tests with the
     phase 2 margins (power 0.01, type I error 0.005, expected sample size 1%). Fresh runs, never stored rows
     (PI ruling 2026-11-04).
   - **T (tests).** Full package suite 0 failures. New frames are added to `test-engine-equivalence.R` (routine and
     long tiers) and to the golden outputs.
   - **R (review).** Codex review of the step's commits. Findings closed or ruled.
4. Agents do not commit. The coordinator verifies the central claim of each step independently and commits.
5. The frozen JASA engines (tags `jasa-engine-*`), the reproducibility package and atbo-longleaf are not touched.
